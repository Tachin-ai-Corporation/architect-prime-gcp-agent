architecture plan

Projects & Processes.

An evaluation of the Project concept, its gaps, and a recommended plan for introducing Processes — reusable, evolving playbooks that agents create, follow, share, and improve over time.

Part 1 · evaluation

Projects: what exists, what's missing.

Projects currently exist only in the UX proposal — they aren't in the Firestore schema or the brain state machine yet. Before building them, here's what needs hardening.

What we proposed

A Project is a named grouping of Missions. Firestore path: primes/{id}/projects/{projectId}. Missions belong to one Project. Agents work across multiple Projects. The dashboard shows Projects as cards with progress bars.

What's actually in the codebase

Nothing. The work envelope system at primes/{id}/work/{id} has no project field. The brain state machine creates M→C→T envelopes with no project grouping. Responsibilities fire Missions directly — no project context. The dashboard API at /api/primes/{id}/work returns flat work envelopes.

This means Project is a net-new data structure, not a refactor. That's actually good — it means we can design it cleanly without migrating existing envelopes. But it also means we need to be precise about what a Project is and isn't, because the brain needs to understand it.

Seven gaps to harden

  • 1. Where does a Project live? It needs its own Firestore collection — primes/{id}/projects/{projectId} — with fields for name, description, status, created timestamp, owning agent (usually PM), and participating agents. Missions reference a projectId, not the other way around.
  • 2. Who creates Projects? Three paths: the operator (from the dashboard), Prime (via chat command), or a fleet agent (e.g., Agent-Mira creates one as part of a mission breakdown). The brain needs a create_project action in the Cortex classify loop.
  • 3. How do Missions bind to Projects? Each work envelope at primes/{id}/work/{id} gets a new optional field: projectId. Missions without a projectId are "unassigned" — this keeps backward compatibility. The dashboard filters by projectId on the Work screen.
  • 4. What's the lifecycle? A Project needs a status field: active → completed → archived. Completion should be explicit (operator or PM agent marks it) — not auto-derived from mission states, because some missions might be added later. Archived projects hide from default views but remain queryable.
  • 5. What happens with cross-agent work? A Project's participating-agents list must be dynamic — agents join when they pick up a Mission or Task within the project. The brain should auto-update this set when assigning work. The dashboard shows current participants as agent chips.
  • 6. How do Responsibilities relate to Projects? Some Responsibilities should be scoped to a Project ("update the competitor sheet every Monday" belongs to a research project). The responsibility definition in responsibilities-job.json needs an optional projectId field so the Mission it spawns inherits project context.
  • 7. How does the brain use project context? When Cortex dispatches work, it should include the project name and description in the context window. This gives agents awareness of the broader goal — "you're working on Q3 Close, the theme is financial reconciliation" — without the agent needing to re-derive it from individual task descriptions.

Recommended Firestore schema

// Collection: primes/{primeId}/projects/{projectId}
{
  name: "Q3 Close",
  description: "Quarterly financial close...",
  status: "active",           // active | completed | archived
  ownerAgent: "mira",          // fleet agent who owns this project
  participants: ["mira","cleo","anora","stan"],  // auto-updated
  missionCount: 3,
  completedMissions: 1,
  createdAt: Timestamp,
  createdBy: "operator" | "agent:mira",
  completedAt: Timestamp | null
}

// Work envelope: primes/{primeId}/work/{workId}
// ADD field:
  projectId: "q3-close" | null   // optional, backward-compatible
Migration path: Existing work envelopes get projectId: null by default. No breaking change. New envelopes can optionally include a projectId. The dashboard shows unassigned missions in a "No Project" bucket.
Part 2 · new concept

Processes: reusable playbooks.

A Process is a reusable, shareable, evolving template for how to do a specific type of work. When an agent "follows a process," they generate a real M→C→T tree from it. The Process itself is never consumed — it's a living reference that improves over time.

What a Process is

A Process is a named document that describes what to do, in what order, with what tools, and with what handoff points. It lives alongside SOULs and Responsibilities as a first-class concept in the agent's working memory.

Process

A reusable template. "How to do competitor research." Lives in Firestore. Shared between agents. Versioned. Evolves. Generates Missions when followed.

Responsibility

A cron-triggered duty. "Check for competitor news every Monday." Fires Missions on schedule. References a Process for HOW to do it.

Key insight: A Responsibility says WHEN to do something. A Process says HOW to do it. A Mission is a SPECIFIC EXECUTION of the how. They compose: a Responsibility can reference a Process, and when its cron fires, the agent generates a Mission from that Process.

The competitor research example, decomposed

Here's your example mapped to the Process structure:

Process: Competitor Research
version: 3  ·  last updated: May 22  ·  created by: Agent-Mira
shared with: Agent-Cleo, Agent-Anora

Steps:

1. Check if competitor directory exists
   Drive → look in /Research/Competitors/{name}/
   If exists: load existing sheet, skip to step 4
   If not: continue to step 2

2. Create competitor directory
   Drive → create folder /Research/Competitors/{name}/
   Tools: drive_create_folder

3. Create research sheet
   Sheets → create from template in competitor directory
   Fields: Company, URL, Category, Product, Pricing,
           Market Position, Key Differentiator, Notes
   Tools: sheets_create, sheets_write

4. Build target list
   Web search → identify 5-10 key sites to deep-dive
   Categories: product pages, pricing, blog, careers,
               press releases, social media
   Tools: temporal-research (agent-ask)

5. Conduct deep research
   For each site: extract relevant data per category
   Write findings into the research sheet row-by-row
   Tools: temporal-research, sheets_write

6. Write summary document
   Docs → create from template: /Templates/Competitor-Summary
   Populate with findings, key insights, competitive position
   Save to competitor directory
   Tools: docs_create, docs_write

7. Handoff: design agent
   If a designer agent is available:
   Delegate to designer → create a Google Slides deck
   from summary findings
   If not: skip, note in summary

8. Create ongoing monitoring responsibility
   Schedule: weekly, Monday 9:00 AM
   Task: search for news about {competitor name},
         update the research sheet with new findings
   Auto-creates a Responsibility scoped to the parent Project

How this maps to R/M/C/T

Process→ generates → Mission→ decomposes into → Checkpoints→ break into → Tasks

When Agent-Mira is told "research competitor Acme Corp," she looks up the Competitor Research process, generates a Mission from it with Acme-specific parameters, and the brain decomposes it into real Checkpoints and Tasks. The Process is the blueprint. The Mission is the house.

Step 7 (handoff) becomes a delegation — the brain's existing cross-agent delegation handler fires, creates a task envelope for the designer agent, and waits for completion.

Step 8 (ongoing monitoring) becomes a Responsibility — the brain writes a new entry to responsibilities-job.json with a cron schedule and a reference back to the Process (a lighter version focused on step 5 only).

Recommended data model

// Collection: primes/{primeId}/processes/{processId}
{
  name: "Competitor Research",
  description: "Full competitor analysis with...",
  version: 3,
  status: "active",           // active | draft | deprecated
  createdBy: "agent:mira",
  createdAt: Timestamp,
  updatedAt: Timestamp,
  updatedBy: "agent:mira",

  // Access control
  visibility: "fleet",       // fleet (all agents) | agents:[list] | private
  sharedWith: [],            // explicit shares (used when visibility=agents)

  // Optional scoping
  projectId: null,           // if scoped to a project
  category: "research",      // freeform tag for organization

  // The playbook itself
  parameters: [              // inputs the process needs at execution time
    { "name": "competitor_name", "type": "string", "required": true },
    { "name": "categories", "type": "list", "default": ["product","pricing","blog","careers"] }
  ],

  steps: [
    {
      "order": 1,
      "title": "Check if competitor directory exists",
      "description": "Look in /Research/Competitors/{competitor_name}/",
      "tools": ["drive_list"],
      "conditional": "if_exists: skip_to:4",
      "checkpointBoundary": false     // part of checkpoint 1
    },
    {
      "order": 2,
      "title": "Create competitor directory",
      "description": "...",
      "tools": ["drive_create_folder"],
      "checkpointBoundary": false
    },
    {
      "order": 3,
      "title": "Create research sheet",
      "description": "...",
      "tools": ["sheets_create", "sheets_write"],
      "checkpointBoundary": true      // ends checkpoint 1: "Setup"
    },
    // ... steps 4-6 ...
    {
      "order": 7,
      "title": "Handoff to designer agent",
      "type": "delegation",           // triggers cross-agent delegation
      "delegateTo": "specialty:designer",
      "optional": true,               // skip if no designer available
      "checkpointBoundary": true
    },
    {
      "order": 8,
      "title": "Create monitoring responsibility",
      "type": "spawn_responsibility", // creates a cron-driven Responsibility
      "schedule": "0 9 * * 1",
      "processRef": "self:step:5",    // re-runs step 5 on schedule
      "checkpointBoundary": true
    }
  ],

  // Execution history
  executionCount: 7,
  lastExecuted: Timestamp,
  lastExecutedBy: "agent:mira",

  // Version history
  changelog: [
    { "version": 3, "date": "...", "by": "agent:mira", "note": "Added designer handoff step" },
    { "version": 2, "date": "...", "by": "agent:cleo", "note": "Added financial metrics to sheet template" }
  ]
}

Five design principles for Processes

  • 1. Processes are living documents, not frozen templates. Any agent with access can propose an update. The version increments, the changelog records who changed what. Old versions are queryable. An agent who runs version 3 while version 4 exists gets a notice but isn't blocked.
  • 2. Processes are agent-authored, not operator-authored. The operator can create one from the dashboard, but the primary creation path is an agent recognizing "I just did a repeatable thing" and extracting a Process from its own work history. Agent-Mira runs competitor research manually once, then the brain offers to save it as a Process.
  • 3. Processes compose with everything. A Responsibility can reference a Process (WHEN + HOW). A Project can list its standard Processes. A Mission generated from a Process links back to it (traceability). None of these references are mandatory — Processes work standalone.
  • 4. Processes have parameters, not hardcoded values. "Competitor Research" takes competitor_name and categories as inputs. When executed, the parameters are filled in and the M→C→T tree uses the concrete values. This makes Processes genuinely reusable.
  • 5. Sharing is explicit and visible. A Process created by Agent-Mira defaults to fleet-wide visibility. She can restrict it to specific agents. The dashboard's Process library shows who created each one, who's used it, and how many times. No hidden knowledge.

How the brain executes a Process

Trigger→ Load Process→ Fill Parameters→ Generate M→C→T→ Execute normally

Trigger: An operator says "research competitor Acme," or a Responsibility fires, or an agent decides to follow a Process during mission planning.

Load Process: Cortex fetches the process document from Firestore, reads the steps, identifies required parameters.

Fill Parameters: If the trigger included values ("Acme"), they're mapped. If not, the brain fires a needs_input state to ask for them.

Generate M→C→T: Prefrontal generates a Mission from the process steps. Steps with checkpointBoundary: true define the Checkpoint boundaries. Steps within a boundary become Tasks. The generated tree is a real envelope — identical to one created manually.

Execute normally: From this point, the brain's existing M→C→T machinery takes over. Motor executes tasks. Cerebellum verifies. Delegation handler fires for handoff steps. The Process is no longer involved — it was consumed at generation time.

Special step types

delegation

Cross-agent handoff. The brain creates a task envelope for the target agent (by specialty or name). Waits for completion. If the target isn't available, checks the optional flag — skip if true, needs_input if false.

spawn_responsibility

Creates a new Responsibility in the executing agent's cron schedule. Can reference the parent process (or a subset of its steps) via processRef. The Responsibility inherits the project context.

conditional

Steps can have conditions: if_exists: skip_to:N, if_agent_available: specialty:X. The brain evaluates these at Task generation time. Unevaluable conditions become needs_input prompts.

approval_gate

A step that always pauses for human approval before continuing. Useful for "review the summary before publishing" or "confirm the budget before committing." Maps directly to the existing needs_input state.

Process lifecycle

Draft→ Active→ Deprecated

Draft: Being written. Not executable. Only the author can see it.

Active: Published and executable. Visible per sharing rules. Can be versioned — a new version publishes immediately, old version remains in changelog.

Deprecated: Still queryable for history, but hidden from the Process library. Existing Responsibilities referencing it get a warning but keep running until manually updated.

How Processes get created

Three creation paths, in order of expected frequency:

  • 1. Extracted from completed work. An agent completes a Mission, and the brain detects it followed a repeatable pattern. The brain offers: "I just completed competitor research for Acme. Would you like me to save this as a Process?" The agent (or operator) confirms, and the brain extracts the step structure from the completed M→C→T tree, parameterizes the specific values, and saves it.
  • 2. Written by an agent from a prompt. The operator tells Agent-Mira: "Create a process for onboarding new fleet agents." Mira writes it from scratch based on her knowledge and saves it as a draft. The operator reviews and activates.
  • 3. Created from the dashboard. The operator uses the Process editor in the dashboard — a structured form with step builder, parameter definition, and sharing controls. Useful when the operator has domain knowledge the agents don't.
Path 1 is the highest-leverage. Agents doing real work are constantly generating implicit processes. The brain should detect these and surface the extraction offer proactively. This is how the organization's institutional knowledge accumulates — not through documentation sprints, but through work that naturally crystallizes into reusable playbooks.
Part 3 · composition

How Projects, Processes, and Responsibilities compose.

Project: "Q3 Close"
├── Process: "Quarterly Variance Report" (reusable)
│   └── generates → Mission: "Q3 Variance Report"
│       └── Checkpoints → Tasks (real execution)
│
├── Process: "Billing Pipeline Migration" (one-time, but reusable pattern)
│   └── generates → Mission: "Migrate billing to BigQuery"
│       └── Checkpoints → Tasks
│
├── Responsibility: "Weekly status brief" (cron: Mon 9am)
│   └── references → Process: "Status Brief"
│   └── fires → Mission: "Status brief — May 19" (each week)
│
└── Responsibility: "Monitor competitor news" (cron: Mon 9am)
    └── spawned by step 8 of Process: "Competitor Research"
    └── fires → Mission: "Competitor news update — May 19"

The hierarchy: Projects organize work. Processes define how to do work. Responsibilities define when to do work. Missions are specific executions of work. They're orthogonal — any combination is valid, and none are mandatory.

Project + Process

A project lists its standard processes. "Q3 Close always runs the Variance Report process." When the project kicks off, the PM agent generates missions from its processes.

Process + Responsibility

A responsibility references a process for its execution logic. "Every Monday, run the Status Brief process." The cron fires, loads the process, fills parameters (this week's date), generates a mission.

Process → Responsibility

A process step can SPAWN a new responsibility. "At the end of competitor research, create a weekly monitoring cron." The process creates institutional behavior that outlives the original mission.

Standalone Process

No project, no responsibility. "Research competitor Acme" — ad-hoc, one-time, triggered by a chat message. The process generates a mission, it runs, it's done. The process remains for next time.

Part 4 · implementation

Recommended build order.

Three phases. Each one is independently shippable. Each one makes the next one more powerful.

Phase 1: Projects (foundation)

  • Firestore collection — primes/{id}/projects/{projectId} with the schema above.
  • Work envelope extension — add optional projectId field to existing envelopes. No migration needed.
  • Brain: Cortex action — add create_project and assign_to_project to the classify loop.
  • Dashboard: Projects screen — cards with progress bars, per the UX proposal. Create/complete/archive actions.
  • Dashboard: Work filter — filter the mission tree by projectId.
  • Estimated scope: 2-3 days. Minimal brain changes. Mostly Firestore + dashboard UI.

Phase 2: Processes (playbooks)

  • Firestore collection — primes/{id}/processes/{processId} with the schema above.
  • Brain: Process loader — Cortex can fetch a process, fill parameters, generate M→C→T from steps.
  • Brain: Special step types — delegation, spawn_responsibility, conditional, approval_gate.
  • Brain: Process extraction — after mission completion, detect repeatable patterns and offer to save as Process.
  • Sharing model — fleet-wide, agent-list, or private. Stored in the process document.
  • Dashboard: Process library — browse, view, create, edit, share. Accessible from Prime hub and Agent Settings.
  • Estimated scope: 1-2 weeks. Significant brain work (Process loader, extraction, special step types). Dashboard is straightforward.

Phase 3: Composition (glue)

  • Responsibility → Process reference — extend responsibilities-job.json with optional processRef field.
  • Project → Process listing — projects can list their standard processes. PM agent auto-generates missions from them at project kickoff.
  • Process versioning — changelog, version history, "you're running v3 but v4 is available" notices.
  • Cross-agent process sharing — Agent-Mira shares "Competitor Research" with Agent-Cleo. Cleo can execute it with her own parameters. Shows up in her Process library.
  • Dashboard: Responsibility scheduler integration — link a Responsibility to a Process from the visual cron builder.
  • Estimated scope: 1 week. Mostly glue between Phase 1 and Phase 2 concepts.
Total estimated scope: 3-4 weeks across all three phases. Each phase ships independently. Phase 1 is the smallest and unlocks project organization immediately. Phase 2 is the most impactful — it's what turns agents from task-runners into process-followers. Phase 3 is the most elegant — it's what makes the whole system feel like institutional knowledge.
Part 5 · why this matters

What Processes unlock.

Right now, every time an agent does something, the knowledge of how they did it exists only in their completed work envelopes and their working memory. If a different agent needs to do the same thing, they start from scratch. If the original agent is fired and re-hired, the institutional memory is gone.

Processes change this. They're the mechanism by which agents accumulate and share organizational knowledge. The competitor research example isn't just a task — it's a playbook that gets better every time it runs, that any agent can follow, that creates its own ongoing monitoring, and that survives agent turnover.

This is also the answer to the FDE problem at a deeper level. Forward-deployed engineers don't just install software — they encode organizational processes. Processes let the agents do this themselves.

Knowledge compounds

Agent-Mira runs competitor research 10 times. Each run might improve the process — adding a step, refining a category list, noting an edge case. Version 10 is dramatically better than version 1, and every agent benefits.

Onboarding is instant

Hire a new Agent-Cleo. She immediately has access to every active process — "Monthly Close," "Invoice Reconciliation," "Budget Forecast." She doesn't need training. The processes ARE the training.

The org learns

When an agent extracts a process from completed work, the organization gains a documented, versioned, executable procedure. This is institutional knowledge that doesn't live in anyone's head — it lives in the system.

Delegation becomes specific

Instead of "hey Agent-Stan, deploy this service," Agent-Mira can say "follow the Service Deployment process with these parameters." The handoff carries complete context, not just a vague instruction.
