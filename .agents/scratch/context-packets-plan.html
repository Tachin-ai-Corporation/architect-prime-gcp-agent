Context Packets.

A Project without context is a label. With context, it's a working environment. This is the plan for structured, referenceable, inheritable context that flows from Projects down through the entire work tree.

The gap

Why Projects need context.

Right now, when the brain dispatches a task under a Mission, the agent's context window contains: SOUL.md, IDENTITY.md, MEMORY.md, the envelope's rolling 400K-token conversation history, and whatever Core Memory the temporal-memory sub-agent recalls.

What it does not contain is: where the project's files live, what sheets exist, which templates to use, what the project's conventions are, who the stakeholders are, or any other persistent context that doesn't fit neatly into a conversation turn or a Core Memory fact.

An agent working on "Q3 Close" has to either remember (from Core Memory) or re-discover (via Drive search) that the variance template lives at /Finance/Templates/Variance-Report-Template, that the budget sheet is budget-q3-2026, and that the leadership folder is /Leadership/Q3-Reports/. Every time. For every task.

This is where knowledge leaks. Core Memory stores facts, but facts aren't context. "The budget sheet exists" is a fact. "This project uses this sheet, this folder, this template, and here's what's in each" is context. Context is structured, referenceable, and inheritable. Facts are flat.
The concept

A Context Packet is a structured environment.

A Context Packet is a JSON object that lives on a Project (or Process, or Mission) and describes the working environment for that scope. It contains typed entries — each one a reference to something real (a Drive folder, a Sheet, a Doc, a URL, a convention, a person) with a summary the brain can read without fetching the resource.

Three properties

  • Typed and structured. Each entry has a kind (drive_folder, sheet, doc, url, person, convention, template, dataset) so the brain knows what it's looking at and which tools can interact with it.
  • Summarized. Every entry carries a brief human-readable summary. The brain reads the summary in its context window; it only fetches the resource when it needs to act on it. This keeps the token cost low and the signal high.
  • Inheritable. A Mission inherits its Project's context. A Task inherits its Mission's context. If the Mission adds its own entries, they merge. If a Mission overrides a Project entry (same key), the override wins. Context flows downhill.

The schema

// Context Packet — lives on a Project, Process, or Mission
"context": {
  // Unique key per entry. Inheritance uses key matching.

  "budget_sheet": {
    "kind": "sheet",
    "ref": "1BxR7a9K_spreadsheetId_here",
    "url": "https://docs.google.com/spreadsheets/d/1BxR7...",
    "name": "Q3 2026 Budget",
    "summary": "Master budget tracker. Tabs: actuals, forecast, variance. Updated weekly by Agent-Cleo. Amounts in USD.",
    "updatedAt": "2026-05-22T14:30:00Z",
    "updatedBy": "agent:cleo"
  },

  "project_folder": {
    "kind": "drive_folder",
    "ref": "1a2b3c_folderId",
    "url": "https://drive.google.com/drive/folders/1a2b3c...",
    "name": "/Finance/Q3-Close/",
    "summary": "Root project folder. Contains: /Reports (variance memos), /Data (raw exports), /Templates (reusable doc templates).",
    "updatedAt": "2026-05-21T10:00:00Z",
    "updatedBy": "agent:mira"
  },

  "variance_template": {
    "kind": "doc",
    "ref": "doc_id_here",

    "summary": "Final deliverables land here. Leadership has viewer access. Do not put drafts here.",
    "updatedBy": "operator"
  },

  "billing_dataset": {
    "kind": "dataset",
    "ref": "project-id.billing_v2",
    "name": "BigQuery billing_v2",
    "summary": "Migrated billing data. Tables: invoices (DATE partitioned on period_start), line_items, adjustments. ~2.3 GB/year. Created May 22.",
    "updatedBy": "agent:stan"
  },

  "stakeholders": {
    "kind": "people",
    "ref": null,
    "summary": "Sarah Chen (Head of Ops, final approver), David Kim (CFO, reads variance memos), Agent-Mira (PM, project owner).",
    "updatedBy": "agent:mira"
  },

  "conventions": {
    "kind": "convention",
    "ref": null,
    "summary": "File naming: YYYY-MM-DD_type_description. Currency: always USD, 2 decimal places. Variance threshold for flagging: > 5%. Report frequency: monthly on the 5th.",
    "updatedBy": "agent:mira"
  }
}
Every entry is a key-value pair. The key is a stable identifier (like budget_sheet) that stays the same even if the summary updates. This is what makes inheritance work — a Mission can override budget_sheet with a different ref if needed, and the key-matching resolves it cleanly.
Entry types

The kind vocabulary.

A fixed set of kinds so the brain knows what tools can interact with each entry. Extensible — new kinds can be added without schema migration.

drive_folder

A Google Drive folder. Ref is folder ID. Summary describes contents and structure. Motor uses drive_list, drive_create to interact.

sheet

A Google Sheet. Ref is spreadsheet ID. Summary describes tabs, column structure, update frequency. Motor uses sheets_read, sheets_write.

doc

A Google Doc. Ref is document ID. Summary describes sections, purpose, whether it's a template or a living document.

dataset

A BigQuery dataset or table. Ref is project.dataset or project.dataset.table. Summary describes schema, partitioning, approximate size.

url

An external URL — a dashboard, a wiki page, a Jira board, a GitHub repo. Ref is the URL. Summary describes what's there and when it's relevant.

template

A reusable template document. Ref is the doc/sheet/slide ID. Summary describes the structure and when to use it. Processes reference templates by context key.

people

Stakeholders, approvers, contacts. Ref is null (no system resource). Summary lists names, roles, and relevance to the project.

convention

A named set of rules — file naming, currency format, review cadence, anything the team has agreed on. Ref is null. Summary is the convention itself.

The kind field is purely semantic — it tells the brain what type of resource this is. The brain doesn't enforce it. An entry with kind: "sheet" and a summary describing the columns is enough for Cortex to know it should dispatch Motor with a sheets_read tool when it needs that data.

Inheritance

Context flows downhill.

Project context+ Mission context= Effective context→ injected into brain

When the brain assembles context for a task dispatch, it merges context packets from the chain: Project → Mission → (optionally) Checkpoint. Lower levels override upper levels on key collision. The merge is shallow — by key, not deep.

// Project context
{ "budget_sheet": { kind: "sheet", ref: "main_budget_id", summary: "Master budget..." },
  "project_folder": { kind: "drive_folder", ref: "root_folder_id", summary: "/Finance/Q3-Close/" } }

// Mission context (billing migration adds its own entries)
{ "billing_dataset": { kind: "dataset", ref: "project.billing_v2", summary: "New BQ dataset..." },
  "project_folder": { kind: "drive_folder", ref: "migration_subfolder_id", summary: "/Finance/Q3-Close/Migration/" } }

// Effective context at task execution time
{ "budget_sheet": ← from Project (no override)
  "project_folder": ← from Mission (overrides Project)
  "billing_dataset": ← from Mission (new entry) }
The override is the key feature. A Mission working in a subfolder overrides project_folder to point there instead of the root. Tasks under that Mission see the subfolder. Tasks under other Missions in the same Project still see the root. No global mutation, no conflict.

What about Processes?

Processes can also carry context packets — these are template context with parameter placeholders. When a Process generates a Mission, its context merges in with concrete values:

// Process: Competitor Research — template context
{ "competitor_folder": {
    kind: "drive_folder",
    ref: null,    // filled at execution time
    name: "/Research/Competitors/{competitor_name}/",
    summary: "Competitor research folder. Created by process. Contains: research sheet, summary doc."
  },
  "research_sheet": {
    kind: "sheet",
    ref: null,    // created during execution, ref backfilled
    summary: "Research data sheet. Columns: Company, URL, Category, Product, Pricing, Key Differentiator."
  }
}

// After the process executes steps 1-3 and creates the resources:
// The brain BACKFILLS the refs with real IDs
{ "competitor_folder": { ref: "real_folder_id", name: "/Research/Competitors/Acme/", ... },
  "research_sheet": { ref: "real_sheet_id", ... } }
Backfilling is critical. When a Process step creates a resource (a folder, a sheet), the brain writes the resulting ID back into the Mission's context packet. Later steps can reference it by key — research_sheet — without re-discovering it. This is how context accumulates during execution.
Brain integration

How context enters the dispatch window.

The brain already assembles context for each dispatch: SOUL.md + IDENTITY.md + MEMORY.md + envelope history (400K rolling budget) + temporal-memory recall. Context packets become a sixth layer — injected after MEMORY.md and before the envelope history, so the agent always knows its working environment before it sees the conversation.

Injection format

## Project Context: Q3 Close

budget_sheet (sheet): Q3 2026 Budget
  ID: 1BxR7a9K... | Updated: May 22 by Agent-Cleo
  Master budget tracker. Tabs: actuals, forecast, variance. Amounts in USD.

project_folder (drive_folder): /Finance/Q3-Close/Migration/
  ID: migration_subfolder_id | Updated: May 23 by Agent-Stan
  Working folder for billing migration. Contains schema files and ETL scripts.

billing_dataset (dataset): project-id.billing_v2
  Updated: May 23 by Agent-Stan
  Migrated billing data. Tables: invoices, line_items, adjustments. ~2.3 GB/year.

conventions: File naming: YYYY-MM-DD_type_description. Currency: USD 2dp. Variance flag: > 5%.

stakeholders: Sarah Chen (Head of Ops, approver), David Kim (CFO, reads memos).

This renders to roughly 300-500 tokens for a well-populated project — negligible against the 400K envelope budget. The brain reads it once per dispatch. It doesn't need to fetch any resources to understand the environment; it fetches only when a task requires it.

Token budgeting

  • Small projects (3-5 entries): ~200 tokens. Invisible in the context window.
  • Medium projects (8-15 entries): ~500 tokens. Still negligible.
  • Large projects (20+ entries): ~1,200 tokens. The brain should summarize or prune low-relevance entries. Prefrontal can select which context entries are relevant to the current task.
  • Safety valve: If the merged context exceeds 2,000 tokens, Prefrontal is dispatched first to select the 10 most relevant entries for the current task. The full packet stays in Firestore; only the selected subset enters the dispatch window.
Lifecycle

Context packets are living documents.

Four ways context gets updated:

  • 1. Operator sets it. From the dashboard's Project detail screen, the operator can add, edit, or remove context entries. A structured form: pick a kind, paste a URL or ID, write a summary. This is the initial seeding path.
  • 2. Agent creates a resource and backfills. When Motor creates a Drive folder, a Sheet, or a Doc during task execution, the brain checks if the current Process or Mission expects that resource (by context key) and writes the real ref back. The agent doesn't decide to do this — the brain does it automatically when a tool call result matches a null-ref context entry.
  • 3. Agent proposes an update. During work, an agent might discover something worth adding — "I found that the legacy billing reports are at /Finance/Legacy/Billing/." The brain writes this as a new context entry on the Mission. At mission completion, new entries can be promoted up to the Project level (with operator approval or PM agent sign-off).
  • 4. Nightly consolidation. During the existing nightly memory consolidation pass, the brain reviews context packets on active projects and prunes stale entries (resource deleted, summary outdated). Summaries can be refreshed by having temporal-memory re-summarize the current state of a resource.
Promotion is key. Context starts specific (on a Mission) and gets promoted to general (on a Project) when it proves durable. Agent-Stan discovers a useful folder during the billing migration. It lives on that Mission. When the mission completes, Agent-Mira (PM) reviews new entries and promotes the useful ones to the Project. The next mission under Q3 Close inherits them automatically.
Storage

Where context lives in Firestore.

Context packets are a field on the existing document — not a subcollection. This keeps reads cheap (one document fetch includes the context) and writes atomic.

// Project document: primes/{id}/projects/{projectId}
{
  name: "Q3 Close",
  status: "active",
  "context": {                     // ← context packet, map field
    "budget_sheet": { kind: "sheet", ref: "...", summary: "...", updatedAt: "...", updatedBy: "..." },
    "project_folder": { ... },
    ...
  },
  ...
}

// Work envelope: primes/{id}/work/{workId}
{
  type: "mission",
  projectId: "q3-close",
  "context": {                     // ← mission-level overrides/additions
    "billing_dataset": { kind: "dataset", ref: "...", summary: "...", ... }
  },
  ...
}

// Process document: primes/{id}/processes/{processId}
{
  name: "Competitor Research",
  "contextTemplate": {             // ← template with null refs, filled at execution
    "competitor_folder": { kind: "drive_folder", ref: null, name: "{competitor_name}/", ... },
    "research_sheet": { kind: "sheet", ref: null, ... }
  },
  ...
}
  • Firestore document size limit: 1 MB. A context packet with 20 entries is roughly 4-8 KB. Plenty of headroom.
  • Reads: Context comes for free when you fetch the Project or Mission document. No additional query.
  • Writes: Atomic with the parent document. Backfilling a ref is a single field update.
  • No subcollection: Context entries don't need their own lifecycle (no individual deletion, no pagination). A map field is the right shape.
Dashboard

How the operator sees and manages context.

The Project detail screen (from the UX proposal) gains a new section: Context. It appears between the project header and the mission list.

  • Visual: Each entry is a compact row — kind icon, name, summary preview (truncated), last-updated-by chip. Click to expand and see the full summary + ref link.
  • Add entry: Button opens a form: pick kind from dropdown, paste URL/ID (auto-detects kind from URL pattern — Drive URLs, Sheet URLs, Doc URLs), write a summary. Save.
  • Edit summary: Inline edit on the expanded row. The summary is the most-edited field — agents and operators refine it as the project evolves.
  • Promotion badge: Entries that originated on a Mission (not the Project) show a "Promote to project" action. Clicking it copies the entry to the Project context so all future missions inherit it.
  • Auto-detect: When an operator pastes a Google Drive URL, the dashboard auto-fetches the resource name via the Drive API and pre-fills the name and kind fields. The operator writes the summary.
Summary

The full picture.

Project: Q3 Close
│
├── context: budget_sheet, project_folder, variance_template,
│            leadership_folder, stakeholders, conventions
│
├── Mission: Billing pipeline migration
│   ├── context: billing_dataset, project_folder (override → subfolder)
│   ├── Checkpoint → Tasks (inherit all of the above)
│   └── brain sees: project context + mission context, merged
│
├── Mission: Variance report
│   ├── context: (none — inherits project context as-is)
│   └── brain sees: project context only
│
└── Process: Competitor Research
    ├── contextTemplate: competitor_folder(null), research_sheet(null)
    └── when executed: generates mission, backfills refs, merges with project context

Context packets are the connective tissue between the abstract (Projects, Processes) and the concrete (Drive folders, Sheets, datasets). They're cheap to store, cheap to read, cheap to inject, and they compound as agents do work — every resource created during execution enriches the context for the next task.

Build order: Context packets ship as part of Phase 1 (Projects). The schema is simple — a map field on existing documents. The brain integration is a single addition to the context assembly pipeline. The dashboard UI is a section on the Project detail screen. The backfill mechanism ships in Phase 2 alongside Processes. Estimated additional scope: 1-2 days on top of the Project work.
